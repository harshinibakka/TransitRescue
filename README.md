# TransitRescue — Hackathon Prototype

TransitRescue is a local Flask + SQLite web prototype for public-transport disruption response. It demonstrates a workflow inspired by general fleet/logistics operations: report an incident, log vehicle/passenger RFID events, record assistance requests, and dispatch a simulated rescue shuttle.

## What works
- Operator dashboard with SQLite-persisted incidents
- Create breakdown incidents and update their status
- Vehicle checkpoint RFID event simulator
- Pseudonymous passenger boarding RFID event simulator
- Rescue shuttle availability and simulated dispatch
- Passenger accessibility / urgent-appointment / alternative-route requests
- Dashboard metrics and recent event history
- Auto-refresh every 10 seconds

## What is simulated
- RFID scans are generated by buttons. No physical reader is connected.
- Shuttle dispatch changes database status and assigns an illustrative ETA. It does not control a vehicle or run an autonomous-driving stack.
- Fleet locations, route/stop names, capacities, delay values and sample incident are demo data.
- The dashboard does not connect to live GPS, transit feeds, VRL systems, or real passenger databases.
- "Autonomous" means a dispatch workflow simulation only. It is not suitable for controlling a real vehicle.

## VRL distinction
This is an independent hackathon concept informed by general fleet-management ideas such as vehicle identification, fleet visibility, maintenance/incident handling and status updates. It is not built by, endorsed by, or connected to VRL Logistics, and it does not reproduce VRL's internal systems. ## Run locally
Requires Python 3.10+.

### Windows
```powershell
cd TransitRescue
py -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
python app.py
```

### macOS / Linux
```bash
cd TransitRescue
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python -m pip install -r requirements.txt
python app.py
```

Open http://127.0.0.1:5000 in your browser.

## Demo script (90 seconds)
1. Show the seeded Route 500 incident.
2. Click **Simulate scan** for a vehicle checkpoint and passenger boarding event.
3. Submit an accessible transport or urgent appointment request.
4. Click **Dispatch rescue** on the incident.
5. Show the shuttle moving to EN_ROUTE and the incident status changing.
6. Click **Complete demo trip** to reset that shuttle to AVAILABLE.
7. Report a second breakdown to show incident creation.
8. Explain what would be needed for real hardware: RFID reader integration, consent/privacy design, verified GPS/GTFS data, routing APIs, and a separately safety-certified autonomous vehicle system.

## Next steps for a stronger MVP
- Add login/role separation for passenger and operator views.
- Integrate real route/stop data (e.g., GTFS where available) and a routing service.
- Add WebSockets for push updates rather than 10-second polling.
- Connect an ESP32/RFID reader using a protected device API.
- Add dispatch constraints: capacity, distance, wheelchair accessibility, and operator approval.
- Add tests, input validation, CSRF protection, rate limits and production configuration before deployment.
